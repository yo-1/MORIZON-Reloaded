## O-04・O-11・O-12・O-14 対応記録（2026-09-17）

`forest_zoning_main_dialog_elements.py`の`run_elements()`（要素計算の実行前検証）に、以下3件のプリフライトチェックを追加した。いずれも**警告・情報提示のみ**で、実際の計算ロジック・CRS処理・グリッド整合処理には一切変更を加えていない。

1. **GRASS Processing Provider事前確認（O-04・O-11）**: `_is_grass_watershed_available()`。保全対象流域が選択されている場合、`QgsApplication.processingRegistry()`で`grass:r.watershed`/`grass7:r.watershed`の登録有無を確認する。未導入なら処理開始前に「プラグイン→プラグインの管理とインストール→GRASSを有効化」という具体的な復旧手順を示して中断する。
2. **地利計算のCRS事前確認（O-12）**: `_confirm_distance_crs_consistency()`。地利が選択されている場合、DEMと既設路網データのCRSを事前に比較し、不一致があれば具体的なCRS値と再投影の対処方法を提示して続行可否を確認する。distance.py側の既存チェック（不一致時にRuntimeErrorで停止）はそのまま安全ネットとして残している。
3. **地位指数の入力データ診断（O-14）**: `_confirm_siteidx_grid_alignment()`。地位指数が選択されている場合、DEMとNPP/SRAD/VTEXの解像度・CRSを`utils.get_tiff_info()`で比較し、差があれば具体的な数値を提示する。siteidx.py内の`_align_parameter_to_dem`が処理中に自動整合するため処理は止まらないが、差が大きいほど補間誤差が増える可能性を事前に知らせ、続行可否を確認する。

## O-15 原因確定・修正適用（2026-09-30、実機ログとコンソール実測に基づく）

2026-09-30のdev5実機テスト（Windows/QGIS 3.44/配布サンプルデータ Zoningkit_SAMPLE_dev5）で、`MORIZON`ログタブに`UIスレッドが約26.6秒応答していませんでした`という警告が記録された。重なった計測区間はすべて`要素計算: UI更新(refresh_elements_ui)`（重なった5区間、各3.1〜3.3秒）で、`refresh_elements_ui`は同区間中に9回連続で呼ばれ、所要時間が2.1s→3.3sへ徐々に増加していた。

**原因（claude.ai側でPythonコンソール実測により確定）**: `QgsProject().instance()`（括弧付き）は呼ぶたびに新しいプロジェクトオブジェクトを生成する。`refresh_elements_ui`は1回のUI更新の中で検証処理を通じてこれを約16回呼び出しており、1回あたり約2秒かかっていた。
- 実測: 旧書式（`QgsProject().instance()`）16回呼び出し = 2.095秒 ／ 新書式（`QgsProject.instance()`）16回呼び出し = 0.0147秒（約140倍）

**修正（2026-09-30、コミット`3262f9f`、パッチはclaude.ai側で作成）**:
1. `QgsProject().instance()` → `QgsProject.instance()`（4箇所: `forest_zoning_main_dialog_elements.py`×2、`forest_zoning_main_dialog_scoring.py`×1、`forest_zoning_main_dialog_aggregate.py`×1）
2. `refresh_elements_ui`内の`get_elements_error_texts()`の2回呼び出しを1回にまとめ、結果を表示とボタン状態の両方に再利用（重複呼び出しの排除）

この修正はQGIS実機では**未検証**（`py_compile`・`static_check.py`の静的確認のみ）。解析ロジック・しきい値・CRS処理・出力名には一切触れていない。

**次回実機テストで確認すべきこと**:
- `UIスレッドが約N秒応答していませんでした`の警告が出ない、または大幅に短くなること
- `要素計算: UI更新(refresh_elements_ui) 完了 (N秒) ※0.3秒以上かかりました`の行がほぼ出なくなること（0.3秒未満は記録されない）
- `FAILED`がないこと

**このパッチに含まれない関連課題（未解決、別コミット・別対応）**:
1. 更新イベントのまとめ（デバウンス）。1操作で`refresh_elements_ui`が4〜9回呼ばれる件。
2. しきい値初期化の重複。要素計算の終了処理で、同じレイヤー（災害リスク/保全対象を含む流域）に対する処理が約60組確認されている。サンプルでは各0.0秒だが、大きなラスターでは全画素統計が60回走る可能性があり、実データで固まる原因の有力候補。
3. `count_NODATA`の警告が残っている可能性。出力列名が10文字で切り詰められ、`count_NODATA`との比較が外れていると推測されるが、コード未確認。
4. `refresh_elements_ui`が1バーストの中で2.1秒から3.2秒へ徐々に遅くなる現象（原因未確認）。

- 誤ったレイヤーへの紐付けは実機で少なくとも1回発生した（スクリーンショットで確認、`レイヤーを自動設定`を押した直後も解消していなかった）
- 最終的には（手順不明のまま）正しい状態に戻った
- `set_scoring_layer_combobox()`（`レイヤーを自動設定`の処理本体、`forest_zoning_main_dialog_scoring.py:337`）は、表示名ではなく実ファイル名（`Y_02_shuzai`等、`_vN`世代対応）でレイヤーを厳密照合する設計になっており、コードを読む限り誤ったレイヤーを選ぶようには見えない。見つからない場合は`combo.setLayer(None)`を呼ぶが、コンボボックスが空欄許可でない設定の場合、`None`を渡しても現在の選択が変わらずそのまま残る可能性があり、これが「誤った選択のまま固着する」経路として疑われる（推定、未確認）

**再現手順の確定（2026-10-08、同日中の再試験）**: 1クリックごとにスクリーンショットを撮る形で再試験したところ、同一手順で**2回連続**、毎回`収益性/地位（カラマツ）`への誤紐付けが再現した。

1. ベースライン: 集材作業効率は正しく`収益性/集材作業効率`、1点<=6.000/2点<=8.000
2. 「集材作業効率」のしきい値を手動で1点<=2.000/2点<=4に編集
3. 要素計算タブで`収益性/集材作業効率`のグループを削除し、「集材作業効率」のみ再計算
4. スコアリングタブに戻った直後: レイヤーが`収益性/地位（カラマツ）`に化けている。しきい値は手順2で編集した2.000/4.000のまま残留表示（新しいレイヤーに合わせて再計算されていない、古い表示が残っているだけ）
5. 「レイヤーを自動設定」を**1回**押す: 正しく`収益性/集材作業効率`に戻り、しきい値も計算済みの初期値6.000/8.000に戻った

**確定**:
- 手順4（誤紐付けの発生）は、MORIZON固有のコードではなく、QGISの`QgsMapLayerComboBox`が「参照先レイヤーがプロジェクトから削除されると、フィルタ条件（ラスターレイヤー）に合う別の適当なレイヤーへ自動的にフォールバックする」一般的な挙動によるものと推定される（推定、QGIS内部の仕様未検証）。2回とも同じ`カラマツ`が選ばれたことから、ランダムではなく決定的な挙動と考えられる。
- 手順5（`レイヤーを自動設定`で確実に直る）は、2回とも100%再現した。前回「押しても直らなかった」という報告は、クリックのタイミングか実施有無の記憶違いだった可能性が高い。

**運用上の結論**: 要素計算を部分的に再実行した後は、**スコアリングタブを開いたら必ず「レイヤーを自動設定」を押してから実行する**ことで、この問題は確実に回避できる。

**リスク評価**: ユーザーがこの手順を知らずにスコアリングを実行すると、誤ったラスターに対して無関係なしきい値で計算が走り、エラーなく誤った出力が保存される可能性がある（O-21のような性能上の問題ではなく、正誤に関わる問題）。ただし確実なワークアラウンドがあるため、優先度は低〜中とする。

## O-22恒久対応実施（dev13、2026-10-08、実機未検証）

ユーザーの指示により恒久対応を実施した。

**方針**: 既存の`set_scoring_layer_combobox()`（手動の「レイヤーを自動設定」ボタン）をそのまま要素計算完了時に自動呼び出しすることは避けた。この関数は全6項目を無条件に再紐付けし、かつ`force=True`でしきい値も強制的に計算済み初期値へ戻すため、部分的な要素計算のたびに**手を加えていない他のパラメータのしきい値まで毎回リセットされてしまう**という、新たな（O-22より影響の大きい）副作用を生む。

**修正内容**:
- `forest_zoning_main_dialog_scoring.py`に新しいメソッド`fix_broken_scoring_layer_bindings()`を追加。6つのスコアリングコンボボックスそれぞれについて、現在の紐付け先レイヤーのソースファイル名が期待するパターン（`Y_01_chii_sugi`等、`_vN`世代対応）と一致するか確認し、**一致しないものだけ**を正しいレイヤーへ再紐付けし、そのパラメータのしきい値だけを再計算する。既に正しく紐付いている項目には一切触れない。
- `forest_zoning_main_dialog_elements.py`の`add_elements_layer_to_project`（要素計算完了時にレイヤーをプロジェクトへ追加する処理）を`@staticmethod`から通常のインスタンスメソッドに変更し、レイヤー追加後に`self.main.scoring.fix_broken_scoring_layer_bindings()`を呼ぶよう変更。例外は捕捉してログのみ出力し、要素計算の完了処理自体は失敗させない。

**検証**: `static_check.py`・`build_plugin_zip.py`のみ実施。QGIS実機では未検証。次の実機テストで、今回と同じ再現手順（グループ削除→部分再計算）を実行し、**「レイヤーを自動設定」を押さなくても**正しいレイヤーに紐付くこと、かつ**他のパラメータのしきい値が変化しないこと**の両方を確認する必要がある。

## O-15 dev14: 起動直後停止の調査、モジュールimportの計測を追加（2026-10-08、実機未検証）

O-15残存項目（プラグイン読込直後、MORIZON未操作時の数秒〜8秒規模の停止）は、2026-10-08の本セッションだけでも6回以上、複数のQGISプロファイン（default・TestFlight）で独立して再現している。原因調査に着手した。

**矛盾の整理（確定）**: いずれの再現例でも、`プラグイン初期化: __init__`・`initGui`のtimed()計測はともに`0.0s`で完了と記録される一方、その直後に数秒間UIスレッドが応答していない。これは、**実際に重い処理が、現在の計測範囲の外で起きている**ことを意味する。

**着目点（確定、コード調査）**: `__init__.py`の`classFactory()`は`from .forest_zoning import ForestZoning`を実行し、これが`forest_zoning.py`のモジュール本体を初めて読み込む。この読み込み自体は、`ForestZoning.__init__()`が呼ばれる**前**に完了しており、従来のtimed()計測はこの読み込みを一切含んでいなかった。

`forest_zoning.py`は16行目で`from .forest_zoning_main_dialog import ForestZoningMainDialog`を実行しており、これは各タブ（要素計算・スコアリング・ゾーニング・集計・印刷）の実装モジュール、`processes/`パッケージ、`utils/__init__.py`を芋づる式に読み込む。`utils/__init__.py`はモジュール直下（関数内ではなく）で`import processing`を実行している。QGISのProcessingフレームワークは、セッション中で初めて触れられたタイミングでプロバイダ（GRASS等）の初期化処理が走ることが知られており、これがこのタイミングと重なっている可能性がある（推定、未確認）。

**対応（診断のみ、挙動不変）**: `forest_zoning.py`で、`diag_log`（`qgis.core`・`qgis.PyQt.QtCore`のみに依存する軽量モジュール）のimportを先に移動し、`forest_zoning_main_dialog`等のimport文自体を`timed()`で囲んだ。これにより、このimportの所要時間が`プラグイン初期化: モジュールimport(forest_zoning_main_dialog等) 完了 (N.Fs)`という形で直接ログに残るようになった。

**未確認**: この区間が実際に数秒かかっているかどうかは、次の実機テストで確認する必要がある。もし短ければ（例えば0.1秒未満）、仮説は否定され、別の原因（QGIS本体側の処理、他プラグインとの初期化順序等）を探る必要がある。

## O-15 dev14実機確認: importコストを直接確認、残り2件は原因未特定のまま（2026-10-09）

**確定**: 実機ログで、`プラグイン初期化: モジュールimport(forest_zoning_main_dialog等)`が**3.3秒**かかっていることを直接確認した。

01:34:29 モジュールimport(forest_zoning_main_dialog等) 完了 (3.3s)   ← 新規計測
01:34:29 プラグイン初期化: __init__ 開始〜完了 (0.0s)
01:34:29 プラグイン初期化: initGui 開始〜完了 (0.0s)

これは`utils/__init__.py`のモジュール直下`import processing`が、このタイミングで`processing`フレームワーク（GRASS等プロバイダ）の初期化コストを負っているという仮説を支持する結果であり、**importコストがMORIZON側のコードに起因することが確定した**。

**未解決（確定、原因は依然不明）**: ただし、これで全ての停止時間を説明できたわけではない。`diag_log.py`の`UiStallWatchdog.check()`を確認したところ、「重なった計測区間」は**その区間自体が原因であることを意味しない**。停止検知の時間窓（前回tickから今回tickまで）に実測終了していたMORIZON側の区間を参考情報として併記しているだけで、因果関係の証拠ではない（コード内コメントにも明記されている）。

今回の2件（01:34:32の2.7秒、01:35:22の3.3秒）は、いずれも「重なった」とされる区間が**すべて実測0.0秒**であり、その区間自体のコードが停止を起こしているのではなく、**その直後に、まだ計測していない何か**（推定：QGIS本体自身の起動処理の続き、または他プラグインの初期化処理。MORIZON自身のコードは`initGui()`・`refresh_elements_ui()`の時点で既に完了している）が走っていると考えられる（推定、未確認）。

**判断確定（2026-10-09、ユーザーと協議の上）**: 他プラグインを無効化した切り分けテストは実施しないことにした。理由：仮に他プラグイン起因だと確認できても、MORIZON側で直せるものではなく、検証の実益がない。よって、importの3.3秒はMORIZON起因と確定、残り2件（2.7秒・3.3秒）はMORIZON自身のコードではなくQGIS本体・他プラグイン起因の可能性が高いという理解のまま、**これ以上のMORIZON側での原因調査は行わない**。O-15はこの理解で区切りとする。

**今後の案内（未実施、優先度低）**: 正式リリース前のドキュメント整備時に、README.mdの「動作に影響しない既知のログメッセージ」節へ案内を追加する余地がある。ユーザーからのフィードバックにより、「他プラグインを無効化して確認してください」という切り分け手順ではなく、**「起動直後、数秒程度QGISの画面が反応しなくなることがありますが、初回のプラグイン読み込み処理によるもので仕様です（異常ではありません）」という趣旨の説明にする**方針とした（2026-10-09）。切り分け手順を示しても、仮に他プラグイン起因と分かってもユーザー側で対処しようがなく、実務上の案内としては「仕様」と伝える方が分かりやすいため。
