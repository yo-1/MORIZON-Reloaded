## O-04・O-11・O-12・O-14 対応記録（2026-09-17）

`forest_zoning_main_dialog_elements.py`の`run_elements()`（要素計算の実行前検証）に、以下3件のプリフライトチェックを追加した。いずれも**警告・情報提示のみ**で、実際の計算ロジック・CRS処理・グリッド整合処理には一切変更を加えていない。

## O-15 原因確定・修正適用（2026-09-30、実機ログとコンソール実測に基づく）

2026-09-30のdev5実機テスト（Windows/QGIS 3.44/配布サンプルデータ Zoningkit_SAMPLE_dev5）で、`MORIZON`ログタブに`UIスレッドが約26.6秒応答していませんでした`という警告が記録された。重なった計測区間はすべて`要素計算: UI更新(refresh_elements_ui)`（重なった5区間、各3.1〜3.3秒）で、`refresh_elements_ui`は同区間中に9回連続で呼ばれ、所要時間が2.1s→3.3sへ徐々に増加していた。

**原因（claude.ai側でPythonコンソール実測により確定）**: `QgsProject().instance()`（括弧付き）は呼ぶたびに新しいプロジェクトオブジェクトを生成する。`refresh_elements_ui`は1回のUI更新の中で検証処理を通じてこれを約16回呼び出しており、1回あたり約2秒かかっていた。
- 実測: 旧書式（`QgsProject().instance()`）16回呼び出し = 2.095秒 ／ 新書式（`QgsProject.instance()`）16回呼び出し = 0.0147秒（約140倍）

**修正（2026-09-30、コミット`3262f9f`、パッチはclaude.ai側で作成）**:
1. `QgsProject().instance()` → `QgsProject.instance()`（4箇所: `forest_zoning_main_dialog_elements.py`×2、`forest_zoning_main_dialog_scoring.py`×1、`forest_zoning_main_dialog_aggregate.py`×1）
2. `refresh_elements_ui`内の`get_elements_error_texts()`の2回呼び出しを1回にまとめ、結果を表示とボタン状態の両方に再利用（重複呼び出しの排除）

この修正はQGIS実機では**未検証**（`py_compile`・`static_check.py`の静的確認のみ）。解析ロジック・しきい値・CRS処理・出力名には一切触れていない。

**次回実機テストで確認すべきこと**:
- `UIスレッドが約N秒応答していませんでした`の警告が出ない、または大幅に短くなること
- `要素計算: UI更新(refresh_elements_ui) 完了 (N秒) ※0.3秒以上かかりました`の行がほぼ出なくなること（0.3秒未満は記録されない）
- `FAILED`がないこと

**このパッチに含まれない関連課題（未解決、別コミット・別対応）**:
1. 更新イベントのまとめ（デバウンス）。1操作で`refresh_elements_ui`が4〜9回呼ばれる件。
2. しきい値初期化の重複。要素計算の終了処理で、同じレイヤー（災害リスク/保全対象を含む流域）に対する処理が約60組確認されている。サンプルでは各0.0秒だが、大きなラスターでは全画素統計が60回走る可能性があり、実データで固まる原因の有力候補。
3. `count_NODATA`の警告が残っている可能性。出力列名が10文字で切り詰められ、`count_NODATA`との比較が外れていると推測されるが、コード未確認。
4. `refresh_elements_ui`が1バーストの中で2.1秒から3.2秒へ徐々に遅くなる現象（原因未確認）。

**事実（dev6ログで確認済み）**: 要素計算の終了処理で、同じレイヤー（災害リスク/保全対象を含む流域）に対する`init_scoring_rlayer_stats()`呼び出しが約50〜60組確認されている。サンプルでは各0.0秒だが、大きなラスターでは`get_initial_thresholds_of()`内の`bandStatistics()`（全画素走査）が数十回走ることになり、固まる原因になりうる（推測、未検証）。

**重複の理由はコード未確認**（`addMapLayer`のたびに6つのコンボボックスの`layerChanged`が連鎖発火している可能性があるが未調査）。

**修正内容**: `ScoringObject`に直近で初期化したレイヤーIDを記録する`last_init_layer_id`を追加し、`init_scoring_rlayer_stats(obj, force=False)`は同一レイヤーIDへの再初期化をスキップするようにした。`force=True`の呼び出し（`init_scoring_ui`内の構築時初期化、`set_scoring_layer_combobox`の一括反映）は従来どおり常に実行する。`back_to_initial_state`は`init_scoring_rlayer_stats`を呼ばないため無改修（従来どおり）。スキップ回数は`count_event()`でログに残る。

**要確認（未検証・実機で判断すること）**: 同一レイヤーへの`layerChanged`の連鎖発火が実際に「ユーザーが手で変えたしきい値を意図せず初期値へ戻す」副作用を起こしていた場合、本修正によってその副作用が無くなる（＝手動編集したしきい値が、連鎖発火によって勝手に初期値へ戻らなくなる）。これは修正の意図した効果だが、逆に言えば「同じレイヤーを選び直すと必ずQuantile初期値に戻る」という従来の目に見える挙動に依存した操作手順があった場合は挙動差になる。実機で、要素計算→スコアリングタブ遷移後に手動でしきい値を変更し、再度同じレイヤーを選択肢から選び直す操作等を行い、意図しない挙動差がないか確認すること。

### C. 「未計測の処理」停止の計測追加・診断のみ（コミット`03c0991`）

**事実**: 起動直後（MORIZONダイアログを開く前）に「重なった計測区間: 未計測の処理」というUI停止警告が複数セッションで記録されている。
- claude.ai側セッション: 13:35:14（11.9秒）、13:36:11（56.7秒）
- Claude Codeセッション（`1271c34`記録、dev6）: 18:50:20（7.0秒）、18:51:38（77.6秒）

同程度の規模の停止が別々のセッションで出ている（推測: 再現性がある可能性。同一原因かは未確認）。

**修正内容（診断のみ、挙動不変）**:
1. `ForestZoning.__init__`・`initGui()`を`timed()`で計測区間化した。ただし`initGui()`自身のQTimer（ウォッチドッグ）は、Qtのイベントループに制御が戻るまで発火できないため、`initGui()`自体が遅い場合でも直後のtickで事後的に「重なった区間」として検出される一方、`initGui()`が高速であれば「MORIZON自身の処理ではない」という消去法の根拠になる。
2. `UiStallWatchdog.check()`に、重なった計測区間が無い場合のフォールバックを追加した。直近に完了した計測区間名と、それが停止開始の何秒前に完了したかを併記する（`diag_log.py`）。因果関係の証拠にはならないが、「MORIZON側の既知の処理は動いていなかった」ことを示す参考情報になる。

**未確認・次回実機テストで見るべきこと**:
- 起動直後の停止が今回も再現するか。
- 再現した場合、`重なった計測区間`に`プラグイン初期化: __init__`または`プラグイン初期化: initGui`が出るか（出れば実際にMORIZON側の処理時間、出なければMORIZON外の要因の可能性が高まる）。
- 再現しない場合、またはフォールバック表示（`未計測の処理（直近の完了区間: ...）`）が出た場合、その内容を記録する。

このセクションの2件はdev6で既に確認済みの実処理中の解消（上記セクション参照）とは独立しており、O-15のステータス「解消確認（要素計算〜集計の実処理中）」には影響しない。

## O-17 他プラグイン実行中のUI停止警告（2026-10-02、claude.ai依頼・実機未検証）

**事実（和田さんの画面の数値からの計算、確定）**: 和田さんがCS立体図プラグイン（別プラグイン）を約39時間実行していた間、MORIZONを一切操作していないにもかかわらず、`MORIZON`ログタブに`UIスレッドが約N秒応答していませんでした`（重なった計測区間: 未計測の処理）という警告が12件記録された。うち大きい6件は3677〜39478秒の連続する停止で、合計132274.7秒（実行時間140564.7秒の約94%）に達した。

**推定**: CS立体図プラグインがメインスレッドをほぼ全時間占有していた（CS立体図側のコードは未確認）。

**問題の切り分け**: ウォッチドッグ自体の検知は正しい（実際にUIスレッドが長時間応答していなかった）。問題は、この**MORIZONが一切関与していない停止**が`MORIZON`タブに`Warning`として出るため、MORIZONの不具合に見えてしまうこと。

**対応方針（claude.ai依頼、dev9で要件1のみ実施。要件2「無効化設定」・要件3「README追記」は対象外・後続）**:

`UiStallWatchdog.check()`の判定を次のように分岐した（`diag_log.py`）。

1. 停止区間がMORIZONの計測区間（`timed()`の記録）と重なる → 従来どおり`Qgis.Warning`。
2. 重ならない、かつ、MORIZONのメインダイアログが開いている、またはMORIZONの処理スレッド実行中（実行ボタン押下〜完了） → `Qgis.Warning`（利用者への影響があり得るため）。
3. 重ならない、かつ、上記のどちらでもない → `Qgis.Info`。文言: `QGISのUIスレッドが約{stalled:.1f}秒応答していませんでした（MORIZONの処理とは重なっていません。QGIS本体・他プラグイン等の可能性があります）`
4. 3のケースでは、起動後の累計（Info件数・合計秒数）を、発生のたびに1行で併記する（10分おき等の定期出力ではなく、発生時点でのサマリとして実装。最小差分のため新規タイマーは追加していない）。

**「ダイアログが開いている」「処理中」の判定方法（実装）**:
- ダイアログの可視判定: `diag_log.py`に`register_dialog_visibility_check(callable)`を追加し、`forest_zoning.py`の`initGui()`内で`self.is_visible_main_dialog`（既存メソッド）を1回だけ登録する。`diag_log.py`はUI側クラスに依存しないよう、呼び出し可能オブジェクト経由で問い合わせる設計にした。未登録の間は「開いていない」として扱う。
- 処理中判定: `diag_log.py`に`processing_active()`（contextmanagerのカウンタ）を追加し、4つの`run_*()`メソッド（要素計算・スコアリング・ゾーニング・集計）の`thread.start(); progress_dialog.exec_()`を囲む形で適用した。ネスト呼び出しに備えてカウンタ方式にしている。

**採用しなかった案**: 「停止が10秒以上なら`Warning`を維持する」は、今回のような数時間規模の他プラグインの停止も`Warning`になってしまうため不採用（claude.aiの依頼どおり）。

**変更していないこと**: 解析ロジック・しきい値・NoData規則・CRS・出力名。dev8の変更（`8a0b074`・`03c0991`・`e082d5e`）。ウォッチドッグの検知方式自体（250msの`QTimer`、閾値2.0秒）。dev8-Cで追加した起動処理の計測（`プラグイン初期化: __init__`／`initGui`）はそのまま残しており、起動直後（ダイアログを開く前）の停止はこの計測と重ならない限りInfoになる（O-15の起動直後停止の切り分けは、dev8-Cの計測が引き続き使える）。

**検証状況**:
- `py_compile`・`static_check.py`成功。
- 疑似QGIS環境（`qgis.core`/`qgis.PyQt.QtCore`を最小スタブ化、スクラッチ領域の使い捨てスクリプトでリポジトリには未コミット）で、`UiStallWatchdog.check()`の4分岐（重なりあり、重なりなし・アイドル、重なりなし・ダイアログ開、重なりなし・処理中）と累計カウンタを検証し、すべて想定どおりの結果だった。

## O-18 集材作業効率（cost.py）のWindowsファイルロック未対応（2026-10-08、dev9実機テスト中に発見、dev10で修正）

**事実（dev9実機テスト、2026-10-08、確定）**: Windows実機で、要素計算を1回成功させた後（出力レイヤーがQGISプロジェクトに読み込まれた状態）、再度要素計算を実行すると、`収益性/集材作業効率`の工程で必ず失敗した。3回連続で同一の再現を確認（20:19:44 / 20:21:43 / 20:22:49、いずれも`FAILED (step=収益性/集材作業効率を計算中): Deleting ...Y_02_shuzai.tif failed: Permission denied`、`cost.py`の`_write_like()`内`drv.Create()`が原因）。

**原因（確定、コード確認済み）**: `processes/raster_writer/cost.py`の`_write_like()`は、既存出力の有無・ロック状態を確認せず直接`gdal.Create(output_path, ...)`を呼んでいた。他の要素（`siteidx.py`・`distance.py`・`savearea.py`・`shc.py`・`zoning.py`）はO-09で導入された共通ヘルパー`resolve_writable_output_path()`（既存ファイルを削除できない場合、`_v2`, `_v3`...の世代付きパスへ自動退避）を使っているが、`cost.py`だけが対象から漏れていた。要素計算実行前の事前チェック（`forest_zoning_main_dialog_elements.py:950`）は「ロックを検知したが安全な新規出力へ継続します」と警告を出すが、この警告は実際に`resolve_writable_output_path()`を使っている要素にしか当てはまらず、`cost.py`には効いていなかった。

**連鎖した症状（推定、ログの時系列から）**: `cost.py`が失敗し続けるため`Y_02_shuzai.tif`が更新されず古いままとなり、スコアリングタブの自動設定がこの古いレイヤーを選択。他の要素（`siteidx`等）は正常に新しいグリッドで`_v2`出力を生成していたため、収益性スコアリング（`profit.py`）が「入力3ラスターのグリッドが一致していません」で失敗した（`profit.py`自体の検証ロジックは正しく機能しており、修正不要）。さらに下流のゾーニング・集計も、古いレイヤー構成のまま処理が進んだ可能性がある（集計時に`count_2`・`count_4`列が不足する警告が出たが、ゾーニングラスタに実際にそのクラスが存在しなかっただけの可能性もあり、実害は未確認）。

**修正（コミット未定、dev10）**: `cost.py`に`resolve_writable_output_path()`を適用し、他の要素と同じ`_v2`退避方式に統一した（`siteidx.py`と同一パターン）。`generate()`・`_generate_ruggedness()`は、実際に書き込まれた（世代付きの可能性がある）パスを返すよう修正した。解析式・しきい値・NoData規則・CRS・出力名は変更していない。

**検証状況**: `py_compile`・`static_check.py`のみ。**この修正自体はQGIS実機では未検証**（この不具合を発見した実機テストセッションの続きとして、次回実機テストで確認予定）。

**未確認のまま残っている点**:
- 集計時の`count_2`・`count_4`列不足警告が、このロック問題の連鎖的影響か、ゾーニング結果として実際にそのクラスが存在しなかっただけかは未確認。
- dev9のテストE（`count_NODATA`誤検知）・テストF（しきい値初期化スキップ）は、この不具合によるログの混乱で未確認のまま。
