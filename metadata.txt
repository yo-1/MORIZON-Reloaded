    林野庁の委託事業を通じて開発された森林ゾーニング支援ツール「もりぞん（MORIZON）」を、現在のQGIS環境で利用できるよう再実装した非公式プラグインです。

    オリジナル版が採用する「林業の収益性」と「山地災害リスク」の両面から森林管理の方向性を検討する考え方と、基本的な処理体系を継承しています。そのうえで、QGIS 3.44への対応、利用できなくなった旧処理の再構築、処理の安定化および操作性の改善を行っています。

    謝辞：オリジナル版は、林野庁の委託事業において、日本森林技術協会がゾーニングの考え方と作業フローを取りまとめ、MIERUNEがQGISプラグインとして実装したものです。オリジナル版の開発に携わった皆様に感謝いたします。

    MORIZON Reloaded is an unofficial compatibility port of the original MORIZON forest zoning plugin for QGIS 3.44, developed by Yoichi Wada as a personal technical initiative. It is not an official modification by the Japan Forest Technology Association or the Forestry Agency of Japan.

    Acknowledgements: The original MORIZON was developed through a project commissioned by the Forestry Agency of Japan, with the zoning workflow organized by the Japan Forest Technology Association and the QGIS plugin implemented by MIERUNE.

changelog=Version 2.3.0-rc3-dev16 (test build, not yet released)
    - Fixed (O-23): processes/raster_writer/distance.py's distance
      calculation no longer rasterizes the road network directly onto
      the DEM's own grid. When the road vector did not fully cover the
      DEM extent, that direct rasterization could burn zero pixels,
      causing gdal.ComputeProximity to fill the entire output with a
      "no target pixel" sentinel value (observed as 65535) instead of
      either correct distances or NoData -- confirmed by reproducing it
      with a synthetic DEM and a real GDAL/GRASS installation. The fix
      rasterizes onto the union of the DEM extent and the road extent
      (snapped to the DEM's own pixel grid, matching the original
      MORIZON's grass7:r.grow.distance approach), runs
      gdal.ComputeProximity there, then crops the DEM's own window out
      by exact integer pixel offset (no resampling needed, since the
      union grid shares the DEM's resolution and pixel alignment).
      Verified against a real SAGA/GRASS/GDAL installation on synthetic
      test cases: (1) when the road is fully inside the DEM extent, the
      new logic is numerically identical (0 difference) to the old
      direct-DEM-grid logic -- no change for the common case; (2) when
      the road extends beyond the DEM extent, the new logic matches a
      real GRASS r.grow.distance run on the same union grid to
      floating-point precision (max diff ~6.5e-05m), resolving the bug.
      See docs/OPEN_ISSUES.md O-23 for the full verification data.
      Not yet exercised on-device.

    Version 2.3.0-rc3-dev15 (test build, not yet released)
    - Fixed (O-24): processes/raster_writer/shc.py's
      _plan_curvature_zevenbergen() no longer doubles the r/t
      (second-derivative) coefficients before computing plan curvature.
      That doubling was introduced as a claimed "legacy SAGA 2.x
      compatibility" correction, but running the actual Zevenbergen &
      Thorne (1987) algorithm via a real SAGA 9.3.1 installation on a
      synthetic DEM showed the doubled formula did not match SAGA's own
      C_PLAN output (correlation 0.990, shipped values ~1.7x too large
      and not a clean linear scaling of the correct value). Removing the
      doubling matches SAGA's real output to floating-point precision
      (correlation 1.000000, max diff 1.07e-08). Cross-checked against
      SAGA's own source (Morphometry.cpp, Set_Zevenbergen /
      Set_From_Polynom): no such doubling exists there either. The
      Gaussian smoothing (circular window) and circular-neighborhood
      standard deviation steps of SHC were independently verified
      against a from-scratch reference convolution and a real GRASS
      r.neighbors run respectively, and both already matched exactly --
      only this one coefficient-doubling line was wrong. This changes
      SHC (地形の複雑さ) output values -- previously overestimated --
      and, downstream, the 災害リスク score and final zoning. See
      docs/OPEN_ISSUES.md O-24 for the full verification methodology.
      Not yet exercised on-device; QGIS/SAGA-based on-device SHC output
      should be re-checked against this build.

    Version 2.3.0-rc3-dev14 (test build, not yet released)
    - Diagnostic only (O-15): previously, __init__()'s timed() span always
      measured 0.0s while a multi-second UI stall was independently
      recorded right around plugin load (7+ reproductions across
      sessions/profiles). That span never covered the module-level
      import of forest_zoning_main_dialog (and everything it pulls in:
      every tab controller, processes/, and utils/__init__.py's
      module-level "import processing", which can trigger QGIS's
      Processing provider initialization the first time any plugin
      touches it in a session) -- that import happens before __init__()
      even starts. Moved diag_log's own import earlier (it only depends
      on qgis.core/qgis.PyQt.QtCore, so this is safe) and wrapped the
      forest_zoning_main_dialog/forest_zoning_settings_dialog/branding
      import in timed(), so this import's actual duration is now logged
      directly instead of being invisible. No behavior change; purely
      additional logging. Not yet exercised on-device.

    Version 2.3.0-rc3-dev13 (test build, not yet released)
    - Fixed (O-22): after element calculation finishes (full or partial),
      the scoring tab's layer comboboxes are now automatically checked
      and, if any is bound to a layer whose source file doesn't match
      what that slot expects (confirmed on-device: a deleted-and-
      recalculated 集材作業効率 slot ended up pointing at an unrelated
      収益性/地位（カラマツ）layer, apparently due to QgsMapLayerComboBox's
      own fallback when its previous layer is removed from the project),
      it is re-bound to the correct layer and its threshold recomputed.
      Unlike the manual "レイヤーを自動設定" button, this new check
      (fix_broken_scoring_layer_bindings) only touches comboboxes that
      are actually wrong -- already-correct bindings, and their
      thresholds, are left untouched, so a partial element recalculation
      no longer silently resets unrelated manually-tuned thresholds.
      Confirmed twice on-device (2026-10-08) that the underlying mis-
      binding reproduces and that clicking レイヤーを自動設定 fixes it;
      this automatic check itself is not yet verified on-device.
    - No analysis formulas, thresholds, NoData rules, CRS treatment, or
      output names were changed; this only corrects which layer the UI
      reads from before scoring runs.

    Version 2.3.0-rc3-dev12 (test build, not yet released)
    - Fixed (O-21): get_initial_thresholds() (threshold Quantile init,
      shared by the scoring tab and zoning tab) now caches its result
      per (layer id, classes_count) in-process. On-device dev11 logs
      showed 災害リスク/保全対象を含む流域's Quantile threshold being
      recomputed 7x in a row every time element calculation finished
      (confirmed twice, identically), because dev8's dedup only covers
      scoring_objs_dict's 5 threshold-adjustable elements and savearea
      is not one of them. The new cache is keyed by layer id, so it
      closes the gap regardless of which UI combobox transiently
      re-queries the same layer. Harmless on sample data (0.0-0.1s per
      call) but could matter on large rasters. Confirmed on-device
      (2026-10-08, TestFlight profile): the repeated calls for this
      layer dropped from 7 in a row to 2 real computations + 1 cache
      hit (a "しきい値初期値のキャッシュ再利用" log line appeared, not
      present before dev12). Did not reach exactly 1 computation
      because two different classes_count values (3 and 2) were both
      seen for this layer -- plausibly the scoring tab's default and
      the zoning tab's explicit classes_count=2 both transiently
      touching it (root cause for that still unconfirmed). No UI-stall
      warning during the actual processing run (O-15/O-17 regression
      clear).
    - No analysis formulas, thresholds, NoData rules, CRS treatment,
      output names, or the dev8 same-combobox dedup were changed; this
      is a pure performance/duplicate-work fix at a lower shared layer.
